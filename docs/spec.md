# zero-password-chrome 기획

이 문서는 크롬 익스텐션에 대해 확정한 내용을 정리한 것이다.
**[계획]** 표시는 하기로 정했지만 아직 구현하지 않은 항목이다.
**[제안]** 표시는 아직 정하지 않은 후보안이다. 하기로 정하면 이 문서를 고친 뒤 구현한다.
화면 시안은 [`design/`](design/) 에 있다. 시안은 시각 참고용이고, 내용이 다르면 이 문서가 우선한다.

---

## 1. 개요

### 1.1 목적

- 0Password 는 비밀번호를 저장하지 않고 사이트별 비밀번호 **규칙**만 모아 두었다가 로그인 화면에서 보여주는 서비스다. 이 저장소는 사용자가 설치하는 크롬 익스텐션이다.
- 사이트마다 규칙이 달라 같은 비밀번호를 못 쓰고, 그래서 로그인할 때 "이 사이트에선 어떻게 바꿔 썼더라"를 잊는다. 규칙을 보면 이 사이트에 쓴 비밀번호를 떠올릴 수 있다.
- 대상 사이트: 한국에서 주로 쓰는 사이트 우선 (국내 서비스에 한정하지 않음).

### 1.2 사용 시나리오

1. 사용자가 사이트의 **로그인 화면**에 들어가면, 익스텐션이 비밀번호 입력란을 찾고 그 사이트의 규칙을 API 에서 받아온다.
2. 비밀번호 입력란에 **포커스하면** 입력란 아래에 규칙을 **한 줄에 하나씩** 보여준다.
3. 사용자가 규칙을 보고 비밀번호를 떠올려 입력하는 동안 각 줄에 충족 여부가 표시된다.
4. 규칙이 없는 사이트에서는 페이지에 아무것도 띄우지 않는다.
5. 익스텐션 아이콘을 누르면 팝업이 현재 탭 사이트의 규칙(또는 "규칙 없음")과 **제보하기** 버튼을 보여준다. 팝업은 입력란 판별 결과와 상관없이 동작한다 (판별이 틀렸을 때 대비).

### 1.3 원칙

- 규칙은 로그인 화면에서만 페이지에 띄운다. 가입·비밀번호 변경 화면은 사이트가 규칙을 직접 보여주므로 띄우지 않는다.
- 입력 중인 비밀번호는 페이지 밖으로 보내거나 저장하지 않는다. 충족 여부 검사는 content script 안에서만 한다. API 에는 호스트 이름만 간다.
- 익스텐션에는 전체 규칙 DB 를 넣지 않고, 방문한 사이트의 규칙만 받아 캐시한다 (db 의 lite 배포판).

### 1.4 로고

- 로고는 null sign(`∅`)을 쓴다 (호승 결정). 지금 `public/icons/` 의 파란 바탕 "0" 아이콘과 시안의 "0P" 표시는 개발 중에 임시로 만든 것이라 바꾼다 **[계획]**.
- 브랜딩은 배경이나 로고 색과 상관없다 (호승 결정). 로고는 놓이는 곳에 맞춰 흰색이든 검은색이든 쓴다.
- 로고는 한 가지 색 벡터다. 색은 따로 정하지 않고 흰색·검은색 어느 쪽으로든 쓴다 (호승 결정). 원(r32) + 끝이 둥근 사선 (호승 결정). 원본은 [`design/logo.svg`](design/logo.svg) (`currentColor`).
- 브라우저 툴바 색은 사용자 테마에 따라 무엇이든 될 수 있으므로 아이콘은 여러 색에 대응해야 한다 (호승 결정). 크롬은 익스텐션에 툴바 색을 알려주지 않고 manifest 에 테마별 아이콘도 없어서, 아이콘 한 장이 모든 색에서 보여야 한다.
- 그래서 익스텐션 아이콘(툴바, 확장 프로그램 관리 화면, 웹스토어)만 **흰 원형 배경 + 검정 로고**를 쓴다 (호승 결정). 배경은 이 아이콘용이고 브랜드 요소가 아니다. 원본 `public/icons/icon.svg` 에서 `icon16.png`, `icon32.png`, `icon48.png`, `icon128.png` 를 만들어 manifest 의 `icons` 와 `action.default_icon` 에 넣는다 **[계획]**. 지금 manifest 에는 32px 가 없어서 추가한다.
- 팝업은 배경 있는 아이콘 이미지를 쓰지 않고, 한 가지 색 로고를 브라우저 테마(밝게/어둡게)에 맞는 글자색으로 그린다 (호승 결정). 규칙 패널 안에는 로고를 넣지 않는다 (입력란 오른쪽 버튼에만 벡터로 쓴다, §4.2).

## 2. 구조

### 2.1 구성 요소

| 구성 요소 | 하는 일 |
| --- | --- |
| content script (`content.ts`) | 모든 페이지에서 돈다. 보이는 `input[type=password]` 를 찾아 판별하고, 로그인 폼이면 background 에 규칙을 요청한다. 규칙 패널을 그린다 **[계획]**. |
| background (`background.ts`, `rules.ts`) | 메시지를 받아 lite 클라이언트로 규칙을 찾는다. 네트워크 요청은 여기서만 한다. |
| popup (`popup.ts`) | 현재 탭의 호스트로 background 에 규칙을 요청해 보여준다 **[계획]**. |

### 2.2 메시지

content script 와 popup 이 background 에 보내는 메시지는 하나다 (`messages.ts`, 구현됨).

- 요청: `{ type: "getRule", hostname }`
- 응답: `{ ok: true, domain, rule }` 또는 `{ ok: false, error: "not_found" | "network" }`
- `domain` 은 실제로 매칭된 db 항목이다. 호스트와 다를 수 있다 (예: `login.coupang.com` → `www.coupang.com`).
- 팝업도 같은 메시지를 쓴다 **[계획]**. 팝업 전용 메시지는 개발 빌드에서만 쓴다 (호승 확인). 프로덕션 빌드의 background 는 이 메시지를 받지 않는다 **[계획]**.
  - `{ type: "devSetApiBaseUrl", url }` → `{ ok: true }`. `url` 이 비어 있으면 기본 주소로 되돌린다.
  - `{ type: "devClearCache" }` → `{ ok: true }`. lite 캐시를 지운다.

### 2.3 조회와 캐시 (구현됨)

이 저장소가 기대는 계약이다. 바꾸려면 db·api 저장소와 같이 바꾼다.

- 규칙 조회는 npm `zero-password` 의 `zero-password/lite` (`createLiteClient`, `findRule`) 를 쓴다. `Rule` 타입과 `checkPassword` 도 같은 패키지에서 가져온다.
- API: `GET https://0password.startergate.dev/api/{domain}` → `200 { domain, rule }` 또는 `404 { error: "not_found" }`. API 는 CORS 를 열지 않으므로 요청은 background 에서 host 권한으로 한다 (api 저장소 참고).
- 도메인 매칭은 lite 가 한다: 호스트 그대로 → 상위 도메인(등록 도메인까지) → `www.` + 등록 도메인.
- `Rule` 항목: `alphabet`, `number`, `specialCharacter`, `combination`, `forbidden`, `length`. 모두 선택 항목 (db 저장소 README 참고).
- 하위 호환 (호승 결정): 규칙 형식은 새 조건을 선택 항목으로만 추가하고, 읽는 쪽은 모르는 항목을 무시한다. 익스텐션은 설치된 시점의 `zero-password` 버전을 번들하므로, API 가 더 새로운 형식의 규칙을 줘도 아는 항목만 문구로 보여주고 검사한다. 모르는 항목 때문에 오류를 내거나 패널을 숨기지 않는다.
- lite 클라이언트(`createLiteClient()`)가 `chrome.storage.local` 에 하루 동안 캐시한다. 규칙 없음(404)도 캐시한다.
- 네트워크·서버 오류는 캐시하지 않고 `network` 로 돌려준다. 다음 페이지 로드에서 다시 시도한다.
- 점이 없는 호스트(`localhost` 등)는 요청 없이 `not_found` 다.
- content script 는 한 페이지에서 규칙을 한 번만 요청한다.

## 3. 입력란 판별 (구현됨)

- 대상: 보이는 `input[type=password]`. DOM 변경(동적 폼, 숨김 해제)이 있으면 200ms 뒤 다시 훑는다.
- 판별 순서: `autocomplete` 힌트 → 제출 버튼 문구 → 폼 문구(제목, 버튼, action, 경로, 페이지 제목) → 비밀번호 칸 개수 → 입력란 이름의 new/confirm 단서.
- 결과는 `login` / `signup` / `change` / `unknown`. 규칙은 `login` 일 때만 조회하고 보여준다 (`shouldShowRule`).
- 개발 빌드에서는 입력란 옆에 판별 결과 배지가 뜨고 입력란에 `data-0password-kind` 속성이 붙는다.

## 4. 로그인 입력란 규칙 패널 **[계획]**

시안: [`design/screens.html`](design/screens.html) 1번.

### 4.1 언제 뜨나

- 판별 결과가 `login` 이고 규칙 조회가 `ok: true` 일 때만 띄운다.
- 비밀번호 입력란에 포커스하면 뜨고, 포커스가 빠지면 닫힌다.
- 규칙이 없거나(`not_found`) 조회에 실패하면(`network`) 페이지에는 아무것도 띄우지 않는다.

### 4.2 위치와 모양

- 입력란 바로 아래(6px 간격)에 붙고, 폭은 입력란에 맞춘다 (최소 240px). 화면 아래에 공간이 없으면 입력란 위에 띄운다.
- 최소한의 정보만 보여준다 (호승 결정): 규칙 한 줄에 하나 (§4.3)와 각 줄 앞의 상태 아이콘 (§4.4)뿐이다. 로고, "비밀번호 규칙" 제목, 도메인, 닫기 버튼은 넣지 않는다.
- 페이지 스타일과 섞이지 않도록 shadow root 안에 그린다. 페이지 스크롤·리사이즈를 따라 위치를 다시 잡는다.
- 패널은 입력란의 포커스를 빼앗지 않는다.
- 규칙이 있으면 비밀번호 입력란 안쪽 오른쪽에 로고 버튼(24px)을 붙인다 (호승 결정, 비밀번호 관리자 앱들과 같은 방식). 이미지가 아니라 벡터 로고만 그린다 (호승 결정). 색은 그 입력란의 글자색(computed `color`)을 따라서 사이트마다 자연스럽게 맞춘다 (호승 확인). 입력란에 이미 오른쪽 아이콘(비밀번호 보기 등)이 있으면 겹치지 않게 그 왼쪽에 둔다 (호승 확인).
- 색: 브라우저 테마(다크 모드)를 따른다 (호승 확인).

### 4.3 규칙을 줄로 바꾸는 방식

규칙 한 줄 문구는 db 가 만든다 (`describeRule`, db 저장소 참고). chrome 은 문구를 직접 만들지 않고 받은 줄을 그대로 그린다. 패널과 팝업이 같은 문구를 쓴다.

- 언어별 문구는 db 가 내장한다 (호승 결정). 나중에 크롬 밖의 클라이언트가 생겨도 문구를 다시 만들지 않게 하려는 것이다. chrome 은 언어만 넘긴다. 넘길 값은 브라우저 UI 언어(`chrome.i18n.getUILanguage()`) (호승 확인). 1.0 은 영어와 한국어를 지원한다 (호승 결정). 둘 다 아닌 언어는 영어로 보여준다 (호승 확인). db 쪽 문구도 같은 두 언어를 갖춰야 한다 (db 저장소 참고).
- 팝업 문구처럼 chrome 이 가진 고정 문구는 `_locales/en/messages.json`, `_locales/ko/messages.json` 으로 둔다 (호승 확인). manifest 의 `default_locale` 은 `en`. 이 문서의 화면 문구는 한국어 기준이고, 영어 문구는 구현할 때 같이 쓴다.
- 각 줄에는 그 줄에 해당하는 위반 코드(`RuleViolation`)가 붙어 온다. 함수 시그니처는 db spec 에서 정한다.

아래 표는 한국어 문구의 예와 순서다. 최종 문구는 db spec 을 따른다. **허용되지만 필수가 아닌 항목(`allow: true, require: false`)은 줄을 만들지 않는다 (호승 확인).** 막는 게 없는 항목은 비밀번호를 떠올리는 데 도움이 안 되기 때문이다.

| 규칙 | 줄 문구 |
| --- | --- |
| `length.min` + `length.max` | `8~16자` |
| `length.min` 만 | `8자 이상` |
| `length.max` 만 | `16자 이하` |
| `alphabet.require` | `영문 포함` |
| `alphabet.uppercase.require` / `lowercase.require` | `영문 대문자 포함` / `영문 소문자 포함` |
| `alphabet.uppercase.allow: false` / `lowercase.allow: false` | `영문 대문자 사용 불가` / `영문 소문자 사용 불가` (둘 다면 `영문 사용 불가`) |
| `number.require` | `숫자 포함` |
| `number.allow: false` | `숫자 사용 불가` |
| `specialCharacter.require` | `특수문자 포함` |
| `specialCharacter.allow: false` | `특수문자 사용 불가` |
| `*.usable` | `특수문자는 ! @ # $ 만` (해당 종류 이름 + 허용 문자) |
| `combination` | `영문·숫자·특수문자 중 2가지 이상` (`of` 순서대로, 없으면 대문자·소문자·숫자·특수문자) |
| `forbidden.characters` | `쓸 수 없는 문자: < > '` |
| `forbidden.maxRepeat: 2` | `같은 문자 3번 연속 불가` |
| `forbidden.maxSequence: 3` | `연속된 문자(abcd, 4321) 4자 이상 불가` |
| `forbidden.id` | `아이디 포함 불가` (§4.4 아이디 검사) |

규칙에 줄이 하나도 안 나오면(모든 항목이 허용·비필수) 패널을 띄우지 않고 입력란 로고만 붙인다 (호승 확인). 팝업에는 "특별한 제한 없음"(영어 "No specific requirements")으로 보여준다 (호승 확인).

### 4.4 충족 여부 표시

검사는 db 의 `checkPassword(rule, password)` 결과(`RuleViolation[]`)를 각 줄에 붙은 위반 코드와 맞춰 한다 (§4.3). 입력값은 content script 안에서만 쓰고 어디에도 보내거나 저장하지 않는다.

상태는 충족과 미충족 둘뿐이다 (호승 결정, "아직" 상태는 두지 않음).

| 상태 | 아이콘 | 언제 |
| --- | --- | --- |
| 충족 | 초록 체크, 문구는 흐리게 | 그 줄의 조건을 채움 |
| 미충족 | 빨간 X, 문구도 빨간색 | 그 줄의 조건을 못 채움. 더 입력하면 채울 수 있는 경우(8자 이상인데 4자)도 포함 |

- `forbidden.id` 줄은 같은 폼(§3 의 폼 묶음) 안의 아이디 입력란 값을 페이지 안에서 읽어 검사한다 (호승 확인). 아이디 값도 비밀번호처럼 밖으로 보내거나 저장하지 않는다.
  - 아이디 칸 찾기 (호승 확인): 비밀번호 칸 앞에 있는 보이는 입력란 중 `autocomplete="username"` 또는 `email` → `type="email"` → name·id·placeholder 에 id/user/email/아이디/이메일 이 들어간 칸 → 비밀번호 칸 바로 앞의 텍스트 칸 순서로 찾는다.
  - 아이디 칸을 못 찾았거나 비어 있으면 (호승 요청): 이 줄은 판정하지 않고 회색 빈 원으로 둔다. 충족으로 치지 않고, 입력란 로고 색에도 반영하지 않는다. 줄 아래에 이유를 작게 적는다 (호승 요청): 못 찾음 "아이디 칸을 찾지 못해 확인하지 않아요", 비어 있음 "아이디를 입력하면 확인해요". 아이디를 단계를 나눠 먼저 받는 로그인 화면(아이디 입력 → 다음 화면에서 비밀번호)이 흔해서, 이전 화면에서 입력한 아이디는 읽지 않는다 (호승 확인). 읽으려면 아이디를 페이지 사이에 저장해야 하기 때문이다. 실제 단계형 로그인 사이트에서 더 테스트한 뒤 다시 검토한다 (호승 요청).
- 입력값이 비어 있으면 판정하지 않고, 각 줄 앞에 회색 빈 원을 둔다 (호승 결정). 빈칸이어도 입력란 오른쪽 로고는 평소 색으로 띄운다.

### 4.5 닫기

- 패널 안에 닫기 버튼은 없다.
- 입력값이 있고 미충족 줄이 하나라도 있으면(§4.4) 입력란 오른쪽 로고를 빨간색으로 바꾼다 (호승 결정). 모두 충족하면 초록색으로 바꾼다 (호승 결정). 입력값이 비면 원래 색으로 돌아온다. 로고가 벡터라 색만 바꾼다. 패널을 닫아 둬도 알 수 있게 하려는 것이다.
- 입력란 오른쪽 로고 버튼을 누르면 패널을 닫고, 다시 누르면 연다. 버튼을 눌러도 입력란 포커스는 유지된다.
- Esc 로도 닫힌다. 입력란에서 포커스가 빠지면 닫히고, 다시 포커스하면 뜬다.
- 사이트별 숨기기는 1.0 에 포함한다 (호승 결정, #3 체크리스트). 숨긴 사이트에서는 입력란 로고와 패널을 모두 띄우지 않는다. 숨긴 사이트 목록(매칭된 `domain` 기준)은 `chrome.storage.local` 에 둔다 **[계획]**.
- 켜고 끄는 곳: 팝업의 규칙 있음 상태에 "이 사이트 입력란에 표시" 스위치를 두고, 그 아래에 "숨긴 사이트 보기" 링크를 둔다 (호승 확인). 구현 전에 시안(`design/screens.html` 2번)에 먼저 반영한다 (호승 요청). 페이지에서 바로 숨기는 버튼은 패널을 최소 정보로 두기 위해 두지 않는다.
- 숨긴 사이트 전체 목록을 볼 수 있어야 한다 (호승 요청). 설정 페이지(manifest `options_ui`)에 숨긴 사이트 목록과 사이트별 "다시 표시" 버튼을 둔다 **[계획]**. 팝업의 "숨긴 사이트 보기" 링크와 확장 프로그램 관리 화면의 "확장 프로그램 옵션"으로 연다. 숨긴 사이트가 없으면 "숨긴 사이트가 없어요". 설정 페이지도 브라우저 테마를 따른다. 시안: [`design/screens.html`](design/screens.html) 3번.

## 5. 팝업 **[계획]**

시안: [`design/screens.html`](design/screens.html) 2번. 폭 320px.

팝업 전체가 브라우저 테마(`prefers-color-scheme`)를 따른다. 머리의 로고는 한 가지 색 SVG 를 글자색(`currentColor`)으로 그린다 (§1.4).

버튼(제보하기, 다시 시도)은 작게 만들어 머리의 "0Password" 오른쪽에 둔다 (호승 결정). 버튼이 없는 상태는 머리에 로고와 이름만 있다.

현재 탭의 URL 에서 호스트를 꺼내 background 에 `getRule` 을 보낸다. 로그인 입력란 판별 결과와 상관없이 동작한다.

| 상태 | 보여주는 것 | 버튼 |
| --- | --- | --- |
| 불러오는 중 | 호스트 + 자리 표시 줄 | 없음 |
| 규칙 있음 | 호스트, "비밀번호 규칙", 규칙 줄 (§4.3 문구, 충족 표시 없음) | 제보하기 |
| 규칙 있음, 상위 도메인 매칭 | 위와 같고 부제를 "`<domain>` 규칙"으로 | 제보하기 |
| 규칙 없음 | "등록된 규칙이 없어요", "GitHub 에서 제보할 수 있어요." | 제보하기 (강조) |
| 조회 실패 | "규칙을 불러오지 못했어요", "연결을 확인해 주세요." | 다시 시도 |
| 웹사이트가 아님 (`http(s)` 가 아닌 탭) | "규칙을 볼 수 없는 페이지예요" | 없음 |

### 5.1 개발 빌드 설정

개발 빌드(`__DEV__`)에서만 팝업 아래에 설정 영역과 DEV 표시를 둔다. 프로덕션 빌드에는 들어가지 않는다.

- API 주소: 입력란 + "기본값으로". 바꾸면 lite 클라이언트를 새 주소로 다시 만든다. 저장 위치는 `chrome.storage.local` (호승 확인).
- 캐시 비우기: lite 캐시를 지운다.

## 6. 제보하기 **[계획]**

- 0Password 는 오픈소스 프로젝트이고 규칙은 기여자들이 모은다. 그래서 "알려주시면 저희가 추가할게요" 같은 운영자 말투는 쓰지 않는다 (호승 결정). 버튼 이름은 "제보하기"로 두고, 문구는 짧게 쓴다.
- 제보에는 비밀번호 입력값을 절대 넣지 않는다.
- 이동 대상: db 저장소의 규칙 요청 이슈 폼(`rule-request.yml`)을 새 탭으로 연다 (호승 결정). 이슈 폼은 각 입력란의 `id` 를 URL 쿼리로 넘기면 채워진 채로 열린다 ([GitHub 문서](https://docs.github.com/en/communities/using-templates-to-encourage-useful-issues-and-pull-requests/syntax-for-githubs-form-schema)).
  - 예: `https://github.com/startergate/zero-password-db/issues/new?template=rule-request.yml&title=[Rule] nid.naver.com&domain=nid.naver.com&page=https://nid.naver.com/nidlogin.login`
  - `title`: `[Rule] <domain>`
  - `domain`: 규칙 있음이면 매칭된 `domain`, 규칙 없음이면 현재 호스트
  - `page`: 현재 탭의 origin + 경로 (질의 문자열과 해시는 뺀다. 로그인 URL 에 토큰이 붙는 경우가 있어서)
  - `rule`: 규칙 있음이면 지금 규칙 JSON
  - `type`(드롭다운): 규칙 있음이면 "Change an existing rule", 없으면 "Add a new site". 드롭다운이 쿼리로 채워지는지는 문서에 분명하지 않아 구현할 때 확인한다.
  - 사이트의 비밀번호 안내 문구와 스크린샷은 제보자가 직접 쓴다.
- 단점: 제보하려면 GitHub 계정이 필요하고 폼이 영어다. 1.0 이후 자체 제보 폼으로 바꿀 수 있다.

## 7. 권한과 개인정보 **[계획]**

웹스토어 출시를 위해 쓰는 권한만 남긴다 (#6). 방문 사이트의 호스트를 API 로 보내는 것이 웹스토어 정책상 웹 활동 데이터 처리에 해당하므로 개인정보처리방침이 필요하다. 방침 페이지는 api 저장소에서 만든다 (api 저장소 참고).

| 항목 | 지금 | 1.0 |
| --- | --- | --- |
| `storage` | 있음 | 유지. lite 캐시 |
| `activeTab` | 있음 (안 씀) | 유지. 팝업이 현재 탭 URL 을 읽는 데 씀 |
| `scripting` | 있음 (안 씀) | 제거 |
| `host_permissions` | `<all_urls>` | `https://0password.startergate.dev/*` 로 좁힘. background 가 API 를 부르는 데 필요 (API 는 CORS 를 열지 않음) |
| `content_scripts.matches` | `<all_urls>` | `http://*/*`, `https://*/*` (호승 확인). 어느 사이트든 로그인 화면일 수 있어서 좁히지 않는다 |

- 개발 빌드에서 API 주소를 바꾸면 그 주소에 대한 host 권한이 필요하다. 그래서 개발 빌드 manifest 만 host 권한 `<all_urls>` 를 유지한다 (호승 확인).
- 웹스토어 개인정보 항목: 방문한 사이트의 호스트 이름을 API 로 보낸다 (웹 활동). 비밀번호, 입력값, 전체 URL 은 보내지 않는다.

## 8. 개발과 테스트

- `npm run dev` / `npm run build` 로 `dist/` 를 만들고 `chrome://extensions` 에서 압축해제된 확장 프로그램으로 로드한다 (README).
- 단위 테스트는 `bun test`. DOM 에 의존하지 않는 로직(판별, 규칙 → 줄 변환, 충족 상태 계산)은 순수 함수로 두고 테스트한다.
- 수동 테스트 페이지(`test-pages/`)는 `bun run serve:test`. 개발 빌드에서는 `<meta name="0password-test-domain">` 으로 조회 도메인을 바꿀 수 있다.
